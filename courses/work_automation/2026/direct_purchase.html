Case Study Walkthrough #2

Automating Purchase Requests by Demonstration

Instead of describing a routine task, we demonstrated it once in the browser. The AI observed the demo, reverse-engineered the DGIST portal's purchase-request form, verified every step live, and generated a standalone script that replays the whole workflow.

🔧 Before You Start: Setup

Three things to install — the AI agent, its bridge into your browser, and the runtime for the generated script.

1

Claude Code — the AI agent that runs in your terminal.

shell
npm install -g @anthropic-ai/claude-code
claude   # 첫 실행 시 Anthropic 계정으로 로그인

Node.js가 없다면 먼저 nodejs.org에서 설치하세요 (macOS: brew install node).

2

Claude in Chrome extension — lets Claude observe and drive your Chrome.

Chrome Web Store에서 "Claude in Chrome"을 설치하고 같은 Anthropic 계정으로 로그인한 뒤, 확장 설정에서 포탈 사이트 접근 권한(portal.dgist.ac.kr, auth.dgist.ac.kr)을 허용하세요. 크롬 창을 여러 개 쓰거나 프로필이 여러 개면, 세션 시작 시 Claude가 어느 브라우저에 연결할지 물어봅니다.

3

Python + Playwright — 생성된 스크립트를 실행할 런타임.

shell
pip install playwright
playwright install chromium
💡 The Key Idea: Show, Don't Tell

Writing a precise spec of a legacy enterprise form is harder than just doing the task once. So the session was framed as programming by demonstration.

💬 The prompt — polished from the actual session, ready to copy

Context:
- 나는 DGIST 포탈(https://portal.dgist.ac.kr)에서 반복적으로 수행하는 업무를 자동화하는 스크립트를 만들려고 해.
- 로그인이 필요하면 https://auth.dgist.ac.kr/login/ 페이지를 열어줘. 비밀번호 입력과 로그인은 보안상 내가 직접 할게.
- 크롬 확장(Claude in Chrome)이 연결되어 있으니 내 크롬 창에서 작업해.

Role:
너는 내가 시범 보이는 업무를 관찰해서, 그 업무를 재현하는 독립 실행 스크립트(Playwright, Python)를 만들어주는 자동화 엔지니어야.

Command:
1. 내가 크롬에서 해당 업무를 한 번 시범 보일게. 내가 "시범 끝"이라고 하면 분석을 시작해.
2. 스크립트를 쓰기 전에 페이지 구조(iframe, 필드, 팝업, 그리드)를 역공학하고, 각 단계를 실제 브라우저에서 검증해. 단, 검증 중에 저장·제출은 하지 마.
3. 매번 바뀌는 값과 고정값을 구분해서 나에게 확인받고, 바뀌는 값만 입력받는 구조로 만들어.
4. 스크립트는 저장 단계까지만 자동화하고, 최종 제출(발주·결재)은 내가 직접 누르도록 남겨둬.
세션에서 실제로 사용한 원본 프롬프트 보기
Context: 현재 나는 포탈에서 반복적으로 수행하는 나의 업무를 자동화 할 스크립트를 만들려고 해. 포탈을 사용하기 위해서는 auth.dgist.ac.kr에서 우선 로그인을 해야 해. 로그인 후에는 포탈에서 작업을 해.
Role: 너는 내가 자동화 하고자 하는 일을 스크립트화 해주는 사람이야.

ⓘ
The human performs the task once, naturally, in their own browser. The AI (Claude Code + the Chrome extension) inspects the resulting pages, figures out how the form actually works underneath, and only then writes code. No screen recording, no selector hunting by hand.
⚠
세션 중 사람이 해야 하는 일 세 가지. ① 로그인 — AI는 비밀번호를 다루지 않으므로 직접 입력합니다. ② 알림창 닫기 — 포탈이 띄우는 네이티브 alert() 창이 떠 있는 동안 자동화가 멈추므로, Claude가 요청하면 직접 닫아주세요 (창에 적힌 문구를 알려주면 대응 로직에 반영됩니다). ③ 최종 제출 — 저장까지 확인한 뒤 발주·결재 버튼은 직접 누릅니다.
🎬 How the Session Unfolded

Six phases, from demonstration to a runnable script.

1

Human demonstration

The user logged in (the AI never touches passwords) and filed a test purchase request the way they always do: header fields, project search popup, budget popup, one item row, two PDF attachments, save. Then simply said "시범 끝" (demo done).

2

Reading the end state

From the finished draft, the AI identified the target screen (apcpScPurcAply), took screenshots, and discovered the form lives inside an iframe (basicIndex.do) with ~170 input fields — a classic legacy jQuery/jqGrid enterprise page.

3

Reverse-engineering the form

Read-only JavaScript probes mapped every field the demo had touched: header inputs (PURC_NM, VEND_NM, REMK…), dropdown codes for purchase/payment type, the item grid's column model, and the file-upload control.

4

Live verification — without saving

On a fresh form, the AI replayed each step for real: filled the header, drove both search popups, added a grid row, and confirmed the total auto-computes. Everything was verified in the actual browser before a single line of the final script was written. Nothing was submitted.

5

Debugging the surprises

Verification surfaced problems no spec would have mentioned — a save button that only exists if you arrive through the portal menu, a popup that rejects you unless a hidden dropdown is set first, and native alert() dialogs that freeze automation entirely.

6

Generating the script

With every step proven, the AI emitted a standalone Playwright (Python) script plus a small JSON file for the values that change per request. The script stops at save; the final order button is deliberately left to the human.

🐛 What Live Verification Uncovered

Each of these would have silently broken a script written from the demo alone.

1

The save button doesn't exist if you open the form by URL. Navigating directly to the form's address renders a button-less, read-only shell. The portal menu opens the same URL as a POST carrying menu-authorization parameters (commonMenuId, commonProgramId). The script replays that POST to get the real form.

2

Popups have a hidden required order. The budget popup looks like four independent dropdowns, but clicking select fails with "지출계획을 선택해 주세요" unless budget category → spending plan → account are chosen in sequence — each choice triggers an AJAX cascade that populates the next dropdown.

3

The item grid is an inline-edit jqGrid. The "new row" button injects a row whose cells are live inputs named {rowId}_GD_NM, {rowId}_APLY_UNTPRC, … — and the row total only computes if you fire the same change/blur events a human keystroke would.

4

Native dialogs freeze everything. The portal loves alert()/confirm(). While one is open, the page is unreachable to automation — mid-session the human had to close a dialog by hand. The generated script auto-accepts and logs every dialog instead.

5

Detail rows only unlock after the first save. The grid's buttons stay hidden on an unsaved form. The demo's end state revealed the true order: save the header first, then add items, then attach files, then save again.

A script anyone in the lab can run — no AI in the loop at execution time.

🧠 Principles You Can Reuse

The same recipe applies to any repetitive portal task.

Principle 1

Demonstrate, don't specify

One real demo carries more truth than a page of requirements — the AI extracts the workflow, the field names, and the fixed-vs-variable split from what you actually did.

Principle 2

Verify live before codifying

Replay every step in the real browser first. All five surprises above were found before the script existed — not as bug reports afterwards.

Principle 3

Keep the human at the boundaries

Passwords are typed by the human; the irreversible final submission is clicked by the human. Automation owns everything in between.

Principle 4

Parameterize only what changes

Department, purchase type, project, budget category are frozen into the script. Each run needs just a small JSON: what you bought, from whom, and the receipts.
